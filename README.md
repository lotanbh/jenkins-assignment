# DevOps CI/CD Pipeline - Jenkins Assignment

מטלת סיום מעשית - בניית קו ייצור אוטומטי מלא ב-Jenkins עבור ארכיטקטורת שני שירותים במתודולוגיית Blue-Green Deployment ללא השבתה (Zero Downtime).

## 🚀 אודות הפרויקט
הפרויקט מורכב משני שירותים מבוססי Node.js (Express):
1. **שירות ה-API (פורט 4000):** שירות Backend פנימי שמחזיר אך ורק JSON ומספק "מחולל תירוצים של DevOps" רנדומלי, בנוסף לנתיב בדיקת בריאות.
2. **שירות ה-Web (פורט 4040):** שירות Frontend שמגיש דפי HTML ו-CSS סטטיים, ומבצע פניות דינמיות (Fetch) אל שירות Backend הפנימי כדי להציג את המידע למשתמש ללא רענון הדף כולו.

---

## 🛠️ ארכיטקטורה ומימוש דרישות המטלה

### 1. מבנה התיקיות והפרדת הרכיבים
הפרויקט מחולק לשתי תיקיות עצמאיות לחלוטין (`api` ו-`web`), כאשר לכל אחת קובץ `package.json` ו-`Dockerfile` משלה. המכולות רצות על רשת Docker ייעודית ומשותפת בשם `app-network`, מה שמאפשר להן לתקשר ביניהן בעזרת שם המכולה הפנימי (למשל `http://api-blue:4000`) וללא שימוש ב-localhost, בדיוק לפי הדרישות.

### 2. חותמת בנייה (Build Args & Environment Variables)
בזמן הבנייה של ה-Docker Images ב-Jenkins, מוזרקים הפרמטרים `BUILD_NUMBER` ומספר ה-Commit המקוצר (`COMMIT_SHA`) דרך `--build-arg`. ה-Dockerfile הופך אותם למשתני סביבה קבועים (ENV) שזמינים לאפליקציה בזמן ריצה, והם מוצגים בנתיב ה-`/health` של שני השירותים וב-Footer של האתר.

### 3. שער כיסוי בדיקות (80% Coverage Gate)
בשלב הבדיקות, קו הייצור מריץ בדיקות יחידה ואינטגרציה בעזרת Jest ו-Supertest. מיד לאחר מכן מורץ סקריפט אוטומטי שכתבתי (`check-coverage.js`) הקורא את קובץ ה-`coverage-summary.json`. אם אחוז כיסוי השורות באחד מהשירותים נמוך מ-80%, הסקריפט מחזיר קוד שגיאה ומכשיל את הבנייה בג'נקינס באדום. (כרגע הפרויקט עומד על 100% כיסוי בשני השירותים).

### 4. התנהגות מותאמת לפי ענף (Branch-based Workflow)
ה-Jenkinsfile מכיל לוגיקה שבודקת את הענף הנוכחי ב-Git:
- בענף `dev`: מתבצעות בדיקות, אימות שער כיסוי ובניית תמונות ה-Docker בלבד (כדי לוודא שהקוד לא שבור).
- בענף `main`: מתבצע התהליך המלא כולל שלב ה-Blue-Green Deployment המעלה את הקוד לייצור.

### 5. העלאה כחול-ירוק ומנגנון חסינות מחבלה (Rollback האוטומטי)
תהליך ה-Deploy מנוהל על ידי סקריפט חכם (`deploy.js`). בכל פעם שקוד נדחף ל-`main`:
1. הסקריפט מזהה איזו סביבה פעילה כרגע בייצור (למשל `GREEN`).
2. הוא מקים את הגרסה החדשה כסביבה הנגדית (`BLUE`) על פורטים זמניים וסודיים (4001 ו-4041) בתוך הרשת המשותפת.
3. **בדיקת בריאות פנימית (Smoke Test):** מורצת מכולת `curl` זמנית בתוך הרשת שבודקת את נתיב ה-`/health` של הגרסה החדשה.
4. **מנגנון Rollback (מבחן החבלה):** אם הגרסה החדשה פגומה או לא מצליחה לתקשר עם ה-API, בדיקת הבריאות נכשלת, המכולות הזמניות נמחקות מיד, וקו הייצור נעצר באדום מבלי לפגוע או להשבית את האתר הישן שעדיין רץ ברקע.
5. **החלפה חלקה (Switch):** אם הגרסה החדשה בריאה, מכולות הבדיקה נמחקות, המכולות הישנות של הייצור מוסרות, והמכולות החדשות עולות בפורטים הראשיים (4000 ו-4040) בשבריר שנייה ובאפס השבתה.

---
### 🏗️ ארכיטקטורת הפריסה: סקריפט דינמי (deploy.js) מול Docker Compose סטטי

בפרויקטים פשוטים יותר של CI/CD, נהוג לעיתים קרובות לייצר תיקיית `jenkins` ייעודית בשורש הפרויקט המכילה קובצי קונפיגורציה סטטיים כגון `Dockerfile` ו-`docker-compose.yml`, ולהסתמך על פקודות כמו `docker compose up --build` כדי לעדכן את הסביבה. 

עם זאת, עבור פרויקט זה נבחרה באופן מודע ארכיטקטורה פרוצדורלית ודינמית המבוססת על סקריפט ה-`deploy.js`, וזאת בשל מספר סיבות ארכיטקטוניות קריטיות:

1. **ניהול מנגנון Blue-Green ו-Zero Downtime:** 
   כלי כמו Docker Compose מתוכנן להביא את ה-Stack כולו למצב סטטי מוגדר מראש. בעת עדכון גרסה, התנהגות ברירת המחדל שלו היא לעצור את המכולה הישנה (הכחולה) ולהרים את החדשה (הירוקה) על אותו הפורט החיצוני. תהליך זה מייצר בהכרח זמן השבתה (Downtime), דבר המפר את הדרישה המרכזית של המטלה. הסקריפט הדינמי מאפשר לנו להרים את הסביבה החדשה לחלוטין בצד, על פורטים זמניים, בזמן שהסביבה הישנה ממשיכה לשרת לקוחות כרגיל.

2. **בדיקות בריאות פנימיות מבודדות (Health Checks):**
   באמצעות הסקריפט, אנו מריצים בדיקת בריאות (Smoke Test) אקטיבית מתוך הרשת הפנימית (`app-network`) באמצעות מכולת קצה זמנית, *לפני* שמבוצע ניתוב מחדש של התנועה. קשה מאוד (ואף מסורבל) לנהל לוגיקה מורכבת של לולאות ניסיונות חוזרים (Retries), השהיות, ותנאי עצירה בצורה הצהרתית (Declarative) בתוך קובץ Compose סטטי.

3. **מנגנון Rollback אוטומטי ומניעת חבלות:**
   במקרה ובדיקת הבריאות נכשלת (למשל במבחן החבלה), הסקריפט יודע לבצע באופן מיידי "התאוששות מכשל": הוא מנקה את השאריות של המכולות הפגומות, משאיר את מכולות הייצור המקוריות יציבות באוויר, ומחזיר סטטוס כשל לג'נקינס. הפרדה זו מבטיחה שהשרת לעולם לא יישאר במצב מידלדל או פגום, ושום תנועה פגומה לא תגיע למשתמשי הקצה.

## ⚙️ הוראות הקמה והרצה

### הפעלת ה-Pipeline ב-Jenkins
1. מקימים פרויקט מסוג **Pipeline** בג'נקינס.
2. תחת הגדרות ה-Pipeline, בוחרים ב-*Definition: Pipeline script from SCM*.
3. בוחרים ב-**Git**, ומדביקים את הקישור למאגר ה-GitHub הזה.
4. מגדירים את ה-*Branch to build* כ-`*/main` (או `*/dev` לבדיקות בלבד).
5. לוחצים על **Build Now**.

### 📌 הערה ארכיטקטונית חשובה לגבי הרצה מקומית ב-Docker
מאחר ושרת הג'נקינס שלי מורץ בעצמו בתוך מכולת Docker (לצורך שמירה על סביבה נקייה ומבודדת), מכולות הבדיקה של ה-Blue-Green קמות ומנוהלות בתוך הסביבה המבודדת של מנוע ה-Docker של ג'נקינס. ה-Pipeline עובר בהצלחה מלאה (SUCCESS) וכל ה-Smoke Tests הפנימיים מאושרים ב-100%.

אם רוצים שהמכולות של האתר יקומו באופן אוטומטי ישירות על המחשב המארח (כך שיופיעו ב-`docker ps` המקומי ויהיו נגישות מיידית ב-`localhost:4040`), יש להרים את מכולת הג'נקינס עם קישור ה-Socket של Docker (Volume Binding) בעזרת הפקודה הבאה:
```bash
docker run -d -p 8020:8080 -v /var/run/docker.sock:/var/run/docker.sock --name jenkins jenkins/jenkins:lts
```

### הרצה ידנית מקומית (Sanity Check)
במידה ורוצים להרים את הגרסה האחרונה של האתר (למשל גרסה 12 שנבנתה בהצלחה) ישירות על ה-Docker המקומי במחשב, ניתן להריץ בטרמינל:
```powershell
# ניקוי שאריות
docker rm -f web-blue web-green api-blue api-green

# הרמת ה-Backend וה-Frontend על הרשת המשותפת
docker run -d --name api-blue --network app-network -p 4000:4000 my-api:12
docker run -d --name web-blue --network app-network -p 4040:4040 -e PORT=4040 -e API_URL=http://api-blue:4000 my-web:12
```
לאחר מכן האתר זמין ופתוח בדפדפן בכתובת: `http://localhost:4040`.
